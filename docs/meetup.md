# Builder Lab host run-of-show

**November 10, 2026 · 6–8 pm Eastern (America/New_York) · Durham Food Hall**

The evening produces a reproducible task-environment experiment: a change to harness, tools, behaviors, system prompt, context, permissions, or evaluation for a small language model. We seek the minimum sufficient intelligence for reliable task performance. A capability is what the package can do. The [care-fit package](../task-environments/care-fit/package.json) is the first example, examining daily afterschool care versus tutoring, drop-in activities, or events with synthetic evidence.

## Before the event

Assign a facilitator, technical helper, and Access domain reviewer. These are roles to fill, not named commitments. The domain reviewer should examine the synthetic expected answers and record reviewer/date/status; until then, describe them as provisional author references. Use the [maintainer checklist](REVIEW_CHECKLIST.md).

On a participant-like laptop, follow the [guide](PARTICIPANT_GUIDE.md), run practice and evaluation, and save the output. Check the actual commands and runtime; a template configuration alone does not establish that a workspace works. Record any blocked checks in [validation](VALIDATION.md).

Prepare an offline repository archive, practice-case printouts, blank result/handoff templates, and one working demonstration laptop. Verify the QR opens the [existing public repository](https://github.com/PublikPrinciple/civikstack-lab-workbench). The repository is the entry point; no hosted coding workspace or model service is promised. Confirm venue logistics separately. Review [hosted readiness](HOSTED_READINESS.md) before describing any proposed Coder/MurMur service as available. Hosted participant packages need verified isolation and access controls; Terraform and prompt instructions alone do not supply that boundary.

## 6:00–6:15 — Introductions and the Access problem (15 minutes)

State the participant job in one sentence: **improve or test one task-environment component and leave reproducible evidence**. Introduce the build, evidence, and test roles. Explain that the source research motivates the problem, while every runnable family/program example is synthetic. State that potential fit does not establish seats, admission, eligibility, or outcomes.

## 6:15–6:30 — Shared examples and evaluation (15 minutes)

Walk through one potential fit, mismatch, and unknown from the practice split. Ask which cited statement supports each answer and which facts remain unknown. Show the package manifest and its prompt/tool/context/permission/evaluation references. Run the deterministic baseline. Show separate correctness, evidence, and unknown-preservation results; explain that there is no single score proving readiness. Explain the public evaluation split and require disclosure of exposure or tuning.

## 6:30–7:30 — Small-group build and review (60 minutes)

- **6:30–6:40:** form groups, inspect the package and available tools, choose one component/question, and run or manually review the baseline.
- **6:40–7:10:** implement one small package change or develop a source/test review. A technical helper resolves setup issues; a domain reviewer records disputed expected answers.
- **7:10–7:25:** evaluate, inspect failures, and fill in the result template. Record resource measurements and unknown measurements honestly.
- **7:25–7:30:** save a progress handoff and prepare a short demo.

A group can propose an approved model/tool or use deterministic rules; the versioned package, contract, and evaluation remain the comparison point. Keep scope to one environment component and show how the change affects behavior or resource needs. The proposed Coder browser workspace and MurMur desktop-model endpoint are unconfigured; the working fallback is local rules or manual review. Do not spend the session provisioning infrastructure or choosing a paid runtime.

## 7:30–8:00 — Demos, failures, and continuation (30 minutes)

- **7:30–7:50:** allocate demo time across groups. Each shows the package component changed, the question, one result with citations, one failure/unknown, and reproduction steps. A manual review counts as a demo.
- **7:50–7:57:** compare disagreements and failure patterns. Identify what needs source review, an added test, or a bounded environment change.
- **7:57–8:00:** confirm where each result and progress handoff is saved, its next task, and whether its author wants it submitted for review. Assign follow-up ownership only when someone agrees.

## Fallbacks

| Problem | Facilitator action | Deliverable still possible |
| --- | --- | --- |
| No Python, installation blocked, or phone only | Pair with a working laptop or supply printed practice cases | Cited expected answer, counterexample, or disagreement record |
| Wi-Fi unavailable | Use the prepared archive and local baseline; distribute printouts | Local result and handoff; submit later |
| Adapter fails or runs too slowly | Record the actual error/time limit and demonstrate the baseline | Reproduction steps, failure analysis, next debugging task |
| Reference answer is disputed | Preserve both interpretations and route to the domain reviewer | Proposed correction with evidence; no silent relabeling |
| Too many groups for individual demos | Use brief paired demos and collect one finding per group | Completed result records for later review |

## After the event

Collect a local review queue without personal records or credentials. Ask authors before publishing their notes or names. Review experiments using the [checklist](REVIEW_CHECKLIST.md), record decisions and unresolved questions, and connect accepted follow-up tasks to the relevant issue or PR. Retain failures as research evidence. A merged contribution is not automatically integrated into Mavis, Beakon, or a public service.

For the next session, contributors read their [progress handoff](PROGRESS_TEMPLATE.md), reproduce the last result, and select the next bounded task. Use the [copyable model prompt](MODEL_PROMPT.md) when resuming with an assistant. No recurring meeting, outreach, or automated follow-up is configured by this plan.
